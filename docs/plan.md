# План: сокращатель ссылок с аналитикой — учебный проект по Claude Code

## Контекст

Пользователь — frontend-разработчик (5 лет опыта), в рамках корпоративного практического курса по Claude Code получил задание построить приложение «сокращатель ссылок с аналитикой». Цель — не просто получить рабочее приложение, а на его материале **последовательно пройти как можно больше повседневных возможностей Claude Code**: CLAUDE.md/rules, plan mode, custom slash-команды, skills, все виды subagents, MCP-серверы, hooks, workflows и loops, а в конце — CI/CD на GitHub Actions.

Технический стек и ключевые продуктовые решения согласованы с пользователем напрямую. Этот документ — общий план-обзор: контекст, архитектура, согласованные решения и карта из 8 этапов. **Детальный план каждого этапа вынесен в отдельный файл** (`stage-N-*.md` в этой же папке) — там конкретные файлы, модули, эндпоинты, команды и шаги верификации. Перед стартом каждого этапа его файл можно скорректировать по факту — детали реализации могут поменяться по ходу проекта, это нормально.

## Согласованные решения

- **Монорепозиторий**: frontend + backend + PostgreSQL в одном репо.
- **Frontend**: Vite + React + TypeScript.
- **Backend**: NestJS.
- **Аналитика**: «средний» уровень — график переходов по дням/неделям, топ referrer, разбор User-Agent (браузер/ОС/тип устройства). Без геолокации по IP.
- **Авторизация**: Google OAuth, у каждого пользователя свои ссылки и своя аналитика.
- **Docker**: обязателен.
- **GitHub**: **сознательно отложен до Этапа 7.** Весь проект (Этапы 1–6) разрабатывается и проверяется полностью локально — код на GitHub не публикуется до тех пор, пока приложение целиком не заработает на машине разработчика. Только в начале Этапа 7 репозиторий создаётся на GitHub, код пушится, и сразу настраивается CI/CD. Причина: нет смысла публиковать и обвешивать автоматизацией код, который ещё не работает целиком — итеративные локальные коммиты дешевле, чем гонять CI на каждом полусыром пуше.
- **Юнит-тесты**: на фронтенде — Vitest + React Testing Library; на бэкенде — Jest (дефолтный тест-раннер NestJS).
- Остальной тулинг — «самое популярное»: pnpm + Turborepo, Prisma, TanStack Query, zustand, shadcn/ui + Tailwind, react-hook-form + zod, recharts.

## Виды агентов Claude Code, которые хотим опробовать по ходу проекта

- **Subagents** — делегированные исполнители в рамках одной сессии (Agent-тул: Explore, Plan, general-purpose, кастомные).
- **Agent view** — единый экран мониторинга фоновых сессий (`claude agents`). Пригодится при нескольких одновременных фоновых задачах/подагентах.
- **Agent teams** — несколько координируемых сессий с общим списком задач и обменом сообщениями под управлением лидера (экспериментальная функция, требует явного включения). Хорошо ложится на достаточно крупную фичу, которую можно распилить на параллельные куски.
- **Dynamic workflows** — скрипт (инструмент Workflow), который запускает много подагентов и взаимно проверяет их результаты; для объёма работы, который не покрыть за один проход.

## MCP-серверы проекта

MCP (Model Context Protocol) подключает Claude Code к внешним системам через отдельные локальные/удалённые серверы — вместо того чтобы гадать по выводу shell-команд, Claude получает специализированные инструменты для конкретной системы. Ниже — все MCP, которые планируется задействовать по ходу проекта, на каком этапе и зачем:

| MCP | Что делает | Этап подключения | Требует аккаунт/ключ? |
|---|---|---|---|
| **PostgreSQL** | Инспекция БД (таблицы, данные, запросы) прямо из чата | 2 | Нет — коннект-строка из `.env` |
| **Context7** | Актуальная документация/примеры кода по версии используемой библиотеки (вместо возможно устаревших знаний модели) | 2 (и далее весь проект) | Нет (опционально API-ключ для более высоких лимитов) |
| **Docker** | Инспекция контейнеров/логов/образов напрямую, без ручных `docker ps`/`docker logs` | 2 | Нет — локальный Docker Desktop |
| **claude-in-chrome** | Визуальное тестирование UI в реальном браузере (скриншоты, клики, консоль) | 3 | Нет — расширение Chrome |
| **Semgrep** | Статический анализ кода на security-паттерны (SQL-инъекции, утечки секретов) | 4 (auth), повторно 6 (QA); MCP подключён на Этапе 7 | Нет — официальный Docker-образ `ghcr.io/semgrep/mcp` (`uvx`/`pip` недоступны в этом окружении, поэтому не через официальный `semgrep-mcp`-путь) |
| **Playwright** | Управление браузером для E2E-тестов | 6 (тесты через CLI), MCP-сервер подключён на Этапе 7 | Нет — `npx @playwright/mcp` |
| **GitHub** | Публикация репозитория, PR, issues, статусы CI прямо из чата | 7 | Да — но не `gh auth login`: официальный локальный Docker-образ `ghcr.io/github/github-mcp-server` со встроенным OAuth (браузерная авторизация без ручного создания токена); удалённый `api.githubcopilot.com/mcp/`-эндпоинт не сработал (не поддерживает dynamic client registration, только PAT или VS Code) |

## Архитектура приложения

### Структура монорепозитория

pnpm workspaces + Turborepo:

```
link-shortener/
├── apps/
│   ├── api/                # NestJS backend
│   └── web/                 # Vite + React frontend
├── packages/
│   └── shared-types/        # общие TS-типы/DTO для FE и BE
├── docker-compose.yml
├── .env.example / .env
├── package.json / pnpm-workspace.yaml / turbo.json
└── README.md
```

`packages/eslint-config` и `packages/tsconfig` (общие ESLint/tsconfig-конфиги для всех воркспейсов) в первоначальном плане закладывались как возможное будущее расширение — по факту не создавались, т.к. пока хватает конфигов на уровне каждого приложения. Заводить их стоит только когда дублирование правил между `apps/api` и `apps/web` реально начнёт мешать.

### Backend (NestJS + Prisma)

ORM — **Prisma v6** (стабильная — v7.9.1 пробовали на Этапе 1, но она требует `prisma.config.ts` и отдельной конфигурации datasource для миграций; для учебного проекта на раннем этапе это лишняя сложность, см. [stage-1-initialization.md](./stage-1-initialization.md)).

Модули: `prisma` (глобальный), `health` (`GET /health`, реализован), `auth` (заготовка — Google OAuth реализуется на Этапе 4), `users` (заготовка), `links` (приватный CRUD ссылок — Этап 2), `redirect` (публичный `GET /:code`, отдельно от `links` — без auth guard, высокочастотный путь — Этап 2), `analytics` (агрегация кликов, парсинг User-Agent — Этап 5).

Схема данных: `User` (googleId, email...), `Link` (originalUrl, shortCode, isCustomAlias, expiresAt, userId...), `Click` (linkId, clickedAt, referrer, browser, os, deviceType), `enum DeviceType`. Полная схема — `apps/api/prisma/schema.prisma`.

### Frontend (Vite + React + TS)

`react-router-dom` v7, `@tanstack/react-query` v5 (серверные данные), `zustand` (только auth/UI-стейт), `shadcn/ui` + Tailwind v4, `react-hook-form` + `zod`, `recharts` для графиков.

Структура: `routes/` (Dashboard, LinkAnalytics, Login, NotFound), `components/ui/` (shadcn), `features/{links,analytics,auth}/`, `lib/` (api-client, query-client), `stores/auth.store.ts`.

### Docker

В docker-compose — **только PostgreSQL** (`postgres:16-alpine`, healthcheck, volume `pgdata`). Backend и frontend на этапе разработки запускаются нативно через `turbo run dev` — сохраняем быстрый HMR.

## Процесс ревью после каждого этапа

Прежде чем отмечать этап ✅ в таблице выше, он проходит **двухзаходное ревью** через skill `/stage-review N` (`.claude/skills/stage-review/SKILL.md`). Все ревью-рассуждения выполняются в **изолированных агентских контекстах** через `Workflow`, не засоряя контекст основной сессии:

1. **Заход 1 (узкий скоуп — диф этапа)**: Параллельно две роли-ревьюера в изолированных контекстах:
   - **code-reviewer**: ищет баги корректности (`git diff stage-(N-1)-done..HEAD`).
   - **security-reviewer**: ищет уязвимости (тот же диапазон).
   
   Затем, если есть находки, запускается **fixer-агент**, который их исправляет, и ревью повторяется. Максимум 3 итерации; если после 3-й всё ещё есть находки — Заход 1 считается неудачным, Заход 2 не запускается.

2. **Заход 2 (широкий скоуп — весь проект целиком)**: Если Заход 1 чист, запускается **integration-reviewer** на полном скане `apps/api/src apps/web/src packages/` (НЕ диф, а полное сканирование). Ловит конфликты между модулями, которые не видны в узком диффе.
   
   **Почему не диф?** Диф показывает только изменённые строки. Но конфликты интеграции часто скрыты в **неизменённых файлах**: функция в модуле A изменила сигнатуру, но неизменённый модуль B всё ещё вызывает её старым способом. Полное сканирование видит обе стороны вместе.
   
   Затем fixer-цикл (макс. 3 итерации, как в Заходе 1).

Оба захода используют **экономный уровень строгости** (эквивалент `code-review` на `medium`): только высокоуверенные, явные баги. Никаких стилистических придирок и спекулятивных «может быть» — это экономит токены и сосредотачивает внимание на реальных проблемах.

**Архитектура: три слоя контекста**:

| Слой | Где выполняется | Что делает | Потребляет контекст сессии? |
|---|---|---|---|
| **SKILL.md** | Основная сессия | Подготавливает аргументы, вызывает Workflow, обрабатывает результат (тег, статусы в доках) | Да, но дёшево |
| **Workflow** (`.claude/workflows/stage-review.js`) | Изолированный Workflow-процесс | Управляет циклами Захода 1 и Захода 2, запускает ревьюеров/фиксера параллельно/последовательно | Нет — свой контекст |
| **agent()** вызовы внутри | Изолированный агент на вызов | Играют роли ревьюера или фиксера | Нет — каждый агент со своим контекстом |

Результат (находки, статус чистоты) возвращается в основную сессию только как структурированный JSON — пошаговые рассуждения ревьюеров остаются в их изолированных контекстах, не засоряя основную сессию.

Только после **чистого Захода 2** ставится git-тег `stage-N-done` (становится базой для Захода 1 следующего этапа) и статус меняется на ✅.

**Опциональная эскалация**: для особо чувствительных этапов (например, Этап 4 — авторизация) пользователь может самостоятельно запустить `/code-review ultra` — многоагентное облачное ревью с перекрёстной проверкой находок. Платно, запускается пользователем напрямую, `stage-review` не вызывает автоматически.

Кастомный subagent `security-reviewer` (заводится на Этапе 4) не заменяет этот процесс — это дополнительная специализированная проверка конкретно auth-кода поверх общего `stage-review`.

## Обязательное обновление документации после этапа

Чистый `/stage-review N` — необходимое, но не достаточное условие для отметки этапа ✅. **Перед тем как считать этап завершённым, вся документация, которую он затронул, обязана быть полностью синхронизирована с фактическим состоянием кода** — не только тег и статус в таблице. Это не опциональный «косметический» шаг, а часть определения «этап завершён».

Что именно проверяется и обновляется на каждом этапе (не только когда что-то явно изменилось по сравнению с планом — **всегда перепроверяется**):

1. **`docs/stage-N-*.md` самого этапа**:
   - Статус в заголовке → ✅ с датой.
   - Если реализация по ходу отклонилась от исходного плана (другой пакет, другое архитектурное решение, найденный и исправленный баг, изменённое название поля/эндпоинта) — это фиксируется отдельным разделом (по образцу «Как выполнялось по факту» в `stage-2-backend-core.md`), а не молча теряется. Будущая сессия должна суметь понять по этому файлу, что реально в коде, не перечитывая весь диф.
   - Таблица «Ключевые файлы», если появились/переименовались/исчезли файлы из первоначального списка.
2. **`docs/plan.md`**:
   - Строка этапа в «Роадмап по этапам» → ✅.
   - Если этап породил новое кросс-проектное решение (новая зависимость, новый MCP-сервер, изменение соглашения, которое коснётся будущих этапов) — заносится в соответствующий раздел («Согласованные решения», таблица MCP-серверов и т.д.), а не остаётся только в тексте stage-файла.
3. **`CLAUDE.md`**: если этап изменил стек, конвенции, структуру файлов, добавил новую известную проблему/грабли (по аналогии с существующими записями про Prisma v7 или `class-validator`) — обязательно отражается здесь. `CLAUDE.md` читается в начале **каждой** будущей сессии как источник истины; устаревший `CLAUDE.md` хуже отсутствующего, потому что ему всё ещё доверяют.
4. **`README.md`**: если поменялись шаги установки/запуска.
5. **Другие `docs/stage-M-*.md` (M > N)**, чьи допущения перестали быть верными из-за решений этого этапа — например, если Этап 2 переименовал поле схемы, а план Этапа 5 ссылается на старое имя, план Этапа 5 обновляется сейчас, а не когда до него дойдёт очередь и всплывёт несостыковка.

**Формулировка правила намеренно жёсткая**: документация никогда не должна одновременно (а) описывать что-то как ещё не сделанное, когда оно уже сделано, или (б) описывать что-то как сделанное определённым способом, когда по факту сделано иначе. Оба состояния одинаково вредны — первое теряет историю решений, второе вводит в заблуждение.

Это применяется к `/stage-review` (Шаг 2 «Обработка результата» в `.claude/skills/stage-review/SKILL.md` выполняет эту синхронизацию как часть финализации чистого прогона) и к любым внеплановым изменениям в ходе сессии — не нужно ждать, пока пользователь явно попросит «обнови доки».
