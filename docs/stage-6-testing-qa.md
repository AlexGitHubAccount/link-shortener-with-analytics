# Этап 6: Тестирование и QA

**Статус**: ✅ Завершён (2026-08-21)

## Цель этапа

Полное покрытие приложения тестами: unit (backend Jest, frontend Vitest+RTL) и E2E (Playwright). Цель — >80% покрытия, все проверки зелёные.

## Темы Claude Code для практики

- **Dynamic workflows** (инструмент Workflow) — параллельная генерация unit-тестов по многим файлам без покрытия, с взаимной проверкой результата: pipeline «сгенерировать тест → верифицировать другим агентом, что тест осмысленный и реально проходит» (а не tautological-заглушка).
- **Agent view** — мониторинг нескольких параллельных фоновых прогонов тестов одним взглядом.
- **`/loop`** — итеративный цикл «прогнать тесты → пофиксить падения → повторить» до зелёного билда.
- **MCP Playwright/Chrome** — для E2E-сценариев.
- **MCP Semgrep** (повторно, уже подключён на Этапе 4) — финальный прогон по всей кодовой базе (не только auth), как часть QA-цикла перед тем, как проект будет считаться готовым к публикации на GitHub.

## Что реализуем

### Backend (Jest)
- `LinksService`: CRUD-логика, генерация и уникальность `shortCode`, edge cases (несуществующий id, конфликт custom-alias).
- `RedirectController`: `404` для несуществующего кода, `410` для истёкшей/неактивной ссылки, `302` с верным `Location`.
- `AnalyticsService`: агрегация — с моками `PrismaService` (groupBy-результаты, проверка корректности `clicksByDay` за пустые дни).
- `AuthService`/`JwtStrategy`: моки Google-профиля, проверка `findOrCreateByGoogleProfile`, валидация JWT payload.
- Файлы: `apps/api/src/**/*.spec.ts` (расположены рядом с тестируемым кодом — стандартная конвенция Nest).

## Пошаговый план работ

1. Установить и настроить Vitest + RTL во фронтенде (см. врезку выше) — без этого шага `pnpm --filter web test` не существует.
2. Workflow-скрипт: параллельная генерация unit-тестов по списку файлов без покрытия; каждый сгенерированный тест верифицируется вторым агентом (реально запускается, проверяется, что не tautological — не просто `expect(true).toBe(true)`).
3. Agent view отслеживает статус параллельных прогонов во время генерации.
4. `/loop` гоняет `pnpm test` по всем воркспейсам до зелёного состояния, автоматически подправляя падения между итерациями.
5. Playwright E2E-сценарий пишется вручную (критичный код полного флоу — не полностью автогенерируется, требует осмысленного проектирования шагов).
6. Финальный прогон Semgrep по всей кодовой базе (`apps/api`, `apps/web`), не только auth.
7. Финальный прогон `pnpm test` + coverage-отчёт, проверка порога >80%.
8. Прогнать `/stage-review 6` (см. `docs/plan.md`) — только после чистого результата статус меняется на ✅. Обязательно выполнить полную синхронизацию документации («Обязательное обновление документации после этапа» в `docs/plan.md`), включая обновление раздела «Testing» в `CLAUDE.md`, если фактическая настройка (coverage-пороги, e2e-раннер) отличается от изначально описанной.

## Как выполнялось по факту

- **Dynamic Workflow для генерации тестов** — `.claude/workflows/generate-tests.js`, новый переиспользуемый workflow (по аналогии с `stage-review.js`). Пайплайн из 3 стадий: генерация (агент пишет и сам прогоняет тест до зелёного) → независимая верификация (**другой** агент перезапускает тест с нуля и явно судит, tautological он или нет) → фикс только для отклонённых. 14 файлов (7 backend + 7 frontend) прошли весь пайплайн, все верифицированы с первой попытки — 0 циклов фикса не потребовалось. Остаток покрытия (~3%: тонкие контроллеры, `PrismaService`, пара веток `GoogleStrategy`) дописан вручную напрямую — гонять ещё один workflow-раунд ради последних процентов не оправдывало накладные расходы.
- **`Agent view`** — отдельного экрана мониторинга как такового не открывалось; прогресс параллельных агентов отслеживался через встроенный прогресс самого `Workflow`-тула (те же данные, другой интерфейс).
- **`/loop`** — не вызывался как отдельная команда; после первого прогона `pnpm test:cov` обнаружилась нехватка ~3% purely branches-покрытия backend — устранено вручную тем же циклом «прогнал → увидел gap → дописал тест → прогнал снова», который `/loop` формализует, просто без отдельного вызова команды.
- **Playwright без `--with-deps`**: в этом окружении нет `sudo` для системных зависимостей (`apt`), которые `--with-deps` пытается поставить. Установлен только сам бинарник браузера (`playwright install chromium`, без флага) — Chromium запускается и работает без проблем даже без системных пакетов.
- **E2E-логин без реального Google-аккаунта**: `apps/e2e/tests/auth-helper.ts` подписывает настоящий JWT тем же `JWT_SECRET`, что использует запущенный backend, сеет реального пользователя в БД через `psql`, и ведёт браузер по реальному `/auth/callback` коду фронтенда (не в обход, а именно через настоящий код, включая настоящий `GET /auth/me`) — единственное, что пропускается, это сам редирект на consent screen Google. Стандартный, широко используемый паттерн для E2E OAuth-защищённых приложений.
- **Реальный баг, пойманный E2E-тестом**: `getByText('1', {exact: true})` в первой версии сценария матчил и счётчик кликов, и подпись на оси графика — неоднозначный локатор. Исправлено на более специфичный CSS-селектор.
- **Финальный Semgrep по всей кодовой базе** (не только auth, как на Этапе 4) нашёл 1 находку: `nestjs-open-redirect` на `redirect.controller.ts` — ожидаемо (редирект на произвольный URL — это и есть весь смысл продукта), но реальным митигейшеном стало явное сужение допустимых протоколов до `http`/`https` в `CreateLinkDto` (`@IsUrl` по умолчанию также пропускает `ftp:` — не нужно продукту вовсе) и синхронно — в zod-схеме `shared-types`, чтобы клиентская валидация не расходилась с серверной.
- **`/stage-review 6` нашёл реальную SQL-инъекцию** в новом E2E-хелпере (`auth-helper.ts` собирал SQL через прямую интерполяцию строк) — fixer применил стандартный паттерн защиты (`psql -v` + `:'var'`-подстановка), но **сломал тест**: оказалось, что `:'var'`-подстановка в этой версии `psql` работает только при подаче SQL через **stdin**, а не через аргумент `-c` (проверено напрямую: идентичный запрос через `-c` даёт `syntax error`, тот же запрос через stdin — работает). Исправлено переводом на `execFileSync(..., {input: sql})`. Урок: автоматический fixer применил концептуально верный security-фикс, но не прогнал сам E2E-тест, который использовал этот код путь — второй прогон `/stage-review 6` после ручного исправления подтвердил, что всё чисто, и заодно поймал мелкий недостающий `?.`-guard в самом `generate-tests.js`.
