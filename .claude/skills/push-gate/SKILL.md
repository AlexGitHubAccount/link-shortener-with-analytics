# push-gate

Заменяет прежний `commit-gate`. Раньше конвейер висел на `git commit` — это неверная точка
привязки: коммит должен оставаться дешёвой, частой, локальной операцией (можно свободно
коммитить, `--amend`, `rebase`, экспериментировать), а не платить AI-конвейером за каждый
чекпоинт. Гейт по весу принадлежит `git push` — это реальная граница, где код покидает вашу
машину (та же граница, на которой стартует CI). `git commit` теперь под отдельным, лёгким
гейтом — только `pnpm lint`, без AI (см. `.claude/hooks/push-gate.sh`, ветка для `git commit`).

Диапазон для ревью — не `git diff --cached` (это для незакоммиченного), а **все локальные
коммиты, которых ещё нет на remote**: `@{u}..HEAD`, если апстрим уже настроен, иначе
merge-base с `origin/main` (первый push новой ветки).

Все ревью-рассуждения и прогоны тестов выполняются в изолированном `Workflow` — не
засоряют контекст основной сессии. Этот skill только готовит аргументы, запускает
workflow, обрабатывает результат и (если чисто) сам делает реальный push.

## Когда срабатывает

- **Автоматически**: вы пытаетесь запушить (командой на естественном языке — «запушь это»,
  «отправь» — или прямым `git push`), hook блокирует голый `git push` с сообщением «invoke
  push-gate now». Увидев этот отказ — запускать этот skill сразу же, без уточнений у
  пользователя.
- **Вручную**: `/push-gate`, если хотите увидеть находки/прогнать тесты до того как решите
  пушить.

## Шаг 0: подготовка

1. Определить диапазон:
   ```
   UPSTREAM=$(git rev-parse --abbrev-ref --symbolic-full-name '@{u}' 2>/dev/null)
   if [ -n "$UPSTREAM" ]; then
     diffBase="$UPSTREAM"
   else
     diffBase="$(git merge-base HEAD origin/main 2>/dev/null || echo HEAD~1)"
   fi
   diffRange="${diffBase}..HEAD"
   ```
   `diffRange`/`diffBase` — символьные выражения (не застывший хэш), передаются в Workflow
   как есть и переразрешаются в актуальный `HEAD` при каждом запуске `git diff` внутри
   агентов — это то, что позволяет фиксеру добавлять коммиты между итерациями без ручного
   пересчёта диапазона.
2. **Docs-only быстрый путь**: `git diff ${diffRange} --name-only` — если ВСЕ файлы в этом
   диапазоне заканчиваются на `.md`, пропустить Шаги 1 и 2.1–2.3 целиком: код-ревьюеры и
   тест-раннеры ничего не находят на чистой прозе, гонять их — просто жечь токены впустую.
   Сразу писать receipt (`git diff ${diffRange} | sha256sum | cut -d' ' -f1 > .claude/.push-gate-passed`)
   и делать `git push`. Если хотя бы один файл не `.md` — идти по обычному пути ниже.
3. Определить, какие области затронуты диапазоном (`git diff ${diffRange} --name-only`),
   чтобы решить, какой глубокий ревьюер подключается дополнительно:
   - тронут `apps/api/src/auth/`, `apps/api/src/common/guards|decorators/`,
     `apps/web/src/features/auth/`, `apps/web/src/stores/auth.store.ts`,
     `apps/web/src/lib/api-client.ts`, `apps/api/src/main.ts` (CORS/security-заголовки/
     ValidationPipe) или `apps/api/src/redirect/` (единственный публичный незащищённый
     эндпоинт) → `needsSecurityDeep = true`
   - тронут `apps/web/src/**` (компонент/страница/фича) → `needsFrontendDeep = true`
   - тронут `apps/api/src/**` (кроме auth/main.ts/redirect выше, они уже покрыты
     security-reviewer'ом) или `apps/api/prisma/**` → `needsBackendDeep = true`
   - тронут `packages/shared-types/**` (FE/BE-контракт: DTO/типы, которые использует и
     бэкенд, и фронтенд) → `needsFrontendDeep = true` **и** `needsBackendDeep = true` разом —
     изменение здесь по определению касается обеих сторон, только один ревьюер увидел бы
     половину картины

## Шаг 1: запуск workflow

Вызвать `Workflow({ name: 'push-gate-pipeline', args: { diffRange, diffBase, needsSecurityDeep, needsFrontendDeep, needsBackendDeep } })`. Workflow (`.claude/workflows/push-gate-pipeline.js`) параллельно:

> Имя workflow — `push-gate-pipeline`, НЕ `push-gate`: последнее принадлежит этому skill'у
> (у skill'ов приоритет в `/`-автокомплите). Skill — точка входа для человека, workflow —
> движок под ним, вызывается только отсюда программно.

- code-reviewer + security-reviewer на `diffRange` (лёгкий, общий проход);
- `agentType: 'security-reviewer'` (глубокий аудит всей security-поверхности — auth + CORS/заголовки/ValidationPipe + публичный redirect-эндпоинт), только если `needsSecurityDeep`;
- `agentType: 'frontend-reviewer'` (a11y + визуальная консистентность + React-гигиена + TanStack Query конвенции + UX форм/роутинга), только если `needsFrontendDeep`;
- `agentType: 'backend-reviewer'` (NestJS + Prisma/БД-корректность + Swagger-консистентность), только если `needsBackendDeep`;
- **affected-test-runner**: определяет и запускает тесты/type-check только для пакетов, затронутых этим диапазоном (Turborepo `--filter` + Jest/Vitest `--changed`), не полный набор;
- **missing-test-writer**: для каждого изменённого файла кода без соответствующего теста — пишет тест, оставляет staged, не коммитит (коммит делает фиксер тем же пакетом, чтобы два субагента не коммитили одновременно);
- **test-quality-verifier** (после барьера параллели, не внутри неё — ему нужно видеть уже дописанные missing-test-writer'ом файлы на диске): **независимо**, отдельным агентом, перепрогоняет и оценивает КАЖДЫЙ тест-файл в диапазоне — не только новые от missing-test-writer, а вообще любой изменённый `*.spec.ts`/`*.test.tsx`. Ловит то, что self-report самого автора теста не ловит: тавтологичные assert'ы (`expect(true).toBe(true)`), тесты ради циферки покрытия, слишком слабые проверки. Это восстановленная половина логики бывшего отдельного `generate-tests.js` («написать → независимо перепроверить → починить») — при переносе в `missing-test-writer` независимая проверка была потеряна, эту находку сделали и исправили в рамках этой же итерации правок.

Если после этого есть находки/красные тесты — **фиксер правит рабочее дерево и делает
ОДИН новый коммит** (`fix: address push-gate findings (iteration N)`) поверх существующей
истории — не amend, не rebase, история остаётся честной. Весь шаг перезапускается с нуля
(диапазон автоматически расширяется, т.к. `HEAD` сдвинулся). До `MAX_ITERATIONS` (15) —
потолок-заглушка от зацикливания, не цель.

Вернёт `{ status: 'clean' | 'dirty', iterations, findings, testFailures, testsWritten }`.

## Шаг 2: обработка результата

- **`status === 'clean'`**:
  1. `git add -A` — если последняя (чистая) итерация была первой и missing-test-writer
     что-то дописал, но фиксер ни разу не запускался, эти файлы всё ещё только staged.
     Если что-то застейджено — закоммитить (`test: add missing coverage (push-gate)`).
  2. **Синхронизация документации** — одна запись в `CHANGELOG.md` (дата, без номера этапа): что сделано, что отличалось от первоначального намерения. Обновить `CLAUDE.md`, если поменялся стек/конвенции/появилась новая грабля. Обновить `README.md`, если поменялись шаги установки. `git add -A` и закоммитить (`docs: sync CHANGELOG/CLAUDE.md/README`), если что-то реально поменялось.
  3. Пересчитать `diffRange` (те же команды, что в Шаге 0.1 — база не меняется, `HEAD` уже включает все новые коммиты) и записать receipt: `git diff ${diffRange} | sha256sum | cut -d' ' -f1 > .claude/.push-gate-passed`.
  4. `git push` — на этот раз hook пропустит (хэш совпадёт с receipt, который сразу же одноразово потребляется).
  5. Сводка пользователю: сколько итераций ушло, сколько коммитов добавил фиксер, что нашли и починили, какие тесты дописаны автоматически, что обновлено в документации.

- **`status === 'dirty'`**:
  1. НЕ пушить, НЕ писать receipt.
  2. Показать `result.findings` / `result.testFailures` — неразрешённые находки и/или незачинившиеся тесты.
  3. Предложить варианты: (а) разобраться самостоятельно, попросить повторить; (б) эскалация `/code-review ultra` для особо чувствительного диапазона (например, auth-код).

## Опциональная эскалация

Для особо чувствительных изменений (например, auth) можно вручную запустить
`/code-review ultra` — глубокое многоагентное облачное ревью. Платно, инициируется
пользователем напрямую. Этот skill не запускает `ultra` автоматически.

Полную регрессию (весь тест-сьют + E2E + build) перед мержем/релизом гоняет CI — см.
`.github/workflows/ci.yml`. Если хочется прогнать её локально вручную до push —
`pnpm test && pnpm --filter e2e test:e2e && pnpm build` напрямую, это не входит в этот skill.
