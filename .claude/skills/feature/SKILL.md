# feature — разработка фичи командой

Вы — **tech-lead** (основная сессия = лид команды; лидом нельзя сделать тиммейта). Ваша
работа — не писать код за команду, а разбить, раздать, состыковать, проверить, отправить.

Требуется включённый флаг `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` (в `.claude/settings.json`).
Если фича мелкая (один файл, один слой) — команда не нужна, скажите это и сделайте напрямую
или одним субагентом.

## Состав команды (1 + 2 + 2)

Как в современной продуктовой команде: разработчики владеют своим кодом целиком, включая
юнит-тесты; отдельный инженер по качеству ревьюит изменения и держит сквозной E2E-набор;
безопасность и пайплайн — отдельным проходом.

**Тиммейты — два разработчика, идут параллельно, роли по границам владения файлами:**

| Тип | Зона | Владеет файлами |
|---|---|---|
| `backend-dev` | `apps/api/src/**` вкл. свои `*.spec.ts`, `apps/api/prisma/**` | сервисы/контроллеры/DTO/миграции + Jest-юниты своей задачи |
| `frontend-dev` | `apps/web/src/**` вкл. свои `*.test.tsx` | страницы/фичи/хуки + Vitest-тесты своей задачи |

«You build it, you test it»: разработчик пишет и держит зелёными свои юнит/компонентные
тесты (`test:cov`, порог 80%).

**`qa-engineer` — инженер по качеству**, две шляпы по фазам:
- **режим ревью** — субагент БЕЗ имени, после готовности фичи (Шаг 4), как и в push-gate:
  корректность, конвенции, явная безопасность, адекватность тестов. Всегда.
- **режим тиммейта** («qa») — спавнится в Шаге 2 ТОЛЬКО если фича добавляет новый
  пользовательский флоу и нужен новый E2E-тест. Владеет `apps/e2e/**` и только им.

**`devsecops-reviewer`** — субагент БЕЗ имени, по условию (Шаг 4). Совмещает security
(auth-поверхность) и devops (CI, Docker, env-переменные, lockfile). Два внутренних прохода,
включается только тот, чью зону diff задел.

**Архитектор — это вы (лид).** Отдельного агента-архитектора нет и не должно быть: решения
о контракте, модели данных, миграционной стратегии, security-постуре, инфре — точки
стыковки между тиммейтами, их принимает координатор (Шаг 1.2). Инфра-файлы (`.github/`,
`Dockerfile*`, `turbo.json`, `docker-compose.yml`, `nginx.conf.template`) редкие и
кросс-слойные — правите их вы напрямую, не тиммейт.

Контракт `packages/shared-types/src/index.ts` — общий; менять его должен ОДИН тиммейт
(обычно backend-dev), остальные ждут (задача-зависимость).

## Шаг 1: план

1. Прочитать `CLAUDE.md` + затронутые области кода.

2. **Архитектурные решения (ваша работа как лида, до разбивки).** Тиммейт реализует, но
   форму задаёте вы. Пройтись по чек-листу и зафиксировать ответы в плане:
   - **Контракт**: нужна ли правка `packages/shared-types/src/index.ts`? Какие именно поля,
     их типы, `null` vs optional (Prisma-модель — источник истины по форме). Кто из тиммейтов
     владеет этой правкой (обычно `backend-dev`), кто ждёт.
   - **Модель данных / миграция**: меняется `schema.prisma`? Деструктив? Тогда expand →
     migrate → contract отдельными миграциями. Новый паттерн выборки по `Click` → нужен
     `@@index` (таблица растёт неограниченно).
   - **Security-постура изменения**: фича трогает auth / guards / `main.ts` / публичный
     `redirect/` / скоупинг по пользователю? Если да — отметить, что Шаг 4 обязан включить
     `devsecops-reviewer`, выдать **одну строку threat-модели** (что атакующий мог бы
     сделать и что это блокирует), и продумать: новый приватный эндпоинт под `JwtAuthGuard`
     + фильтр по `@CurrentUser()`; новый публичный — под `ThrottlerGuard`.
   - **Инфра / путь в прод**: фича добавляет env-переменную, зависимость, меняет `turbo.json`
     / `Dockerfile*` / `.github/workflows/`? Если да — это ваша правка (не тиммейта), и Шаг 4
     обязан включить `devsecops-reviewer` (devops-проход). Новая env-переменная идёт СРАЗУ в
     Joi-схему `config/env.validation.ts` + нужную job в `ci.yml` + `.env.example` (+ Dockerfile,
     если нужна в build/runtime).
   - **Семантика ошибок**: какие Nest-исключения бросаем на каких путях, что видит фронтенд.
   - **Влияние на существующее**: какие текущие тесты/эндпоинты/типы поедут от этой правки.

3. Разбить фичу на задачи так, чтобы **никакие два тиммейта не трогали один файл** (ключевое
   требование Agent Teams — параллельная запись в один файл = потеря изменений). Типичная
   разбивка:
   - контракт в `shared-types` (если нужен) →
   - backend: схема/миграция → сервис → контроллер → DTO + Jest-юниты (тот же тиммейт) →
   - frontend: хук `features/<домен>/useX.ts` → компонент/страница + Vitest-тесты (тот же
     тиммейт) →
   - **новый E2E** (`qa`) — отдельная задача, ТОЛЬКО если фича добавляет новый
     пользовательский флоу; зависит от реализации be/fe.
4. Оформить как общий task-list с зависимостями: frontend-задача, потребляющая DTO, зависит
   от backend-задачи; каждый тиммейт закрывает реализацию вместе со своими юнит-тестами.
5. Показать план пользователю до спавна.

## Шаг 2: спавн тиммейтов

Спавнить по типам, с конкретным контекстом в промпте (тиммейт не видит вашу историю):
```
Spawn a backend-dev teammate named "be". Task: <что именно, какие файлы, какой контракт>.
Include the Jest unit specs for this code.
Spawn a frontend-dev teammate named "fe". Task: <...>. Depends on "be" finishing the DTO.
Include the Vitest tests for this code.
# только если фича добавляет новый пользовательский флоу:
Spawn a qa-engineer teammate named "qa". Task: write the E2E flow test in apps/e2e/**.
Depends on "be" and "fe".
```
Два разработчика (+ `qa` только под новый E2E) — потолок для типичной фичи. Инфра-правки
(env-переменная, CI, Docker) делаете вы сами, не тиммейт. Не начинать реализацию за них —
если поймали себя на этом, вернуться к координации.

## Шаг 3: координация

- Мониторить прогресс через agent-панель / task-list.
- Решать кросс-слойные вопросы (форма контракта, имя поля, семантика ошибки) — это ваша
  работа, не тиммейта.
- Тиммейт застрял/упал → дать инструкции напрямую или заспавнить замену.
- Дождаться, пока ВСЕ задачи закрыты, прежде чем идти дальше.

## Шаг 4: ревью (субагенты без имени, не тиммейты)

Когда ВСЕ задачи закрыты (тиммейт `qa`, если был, завершился) — запустить ревьюеров как
**субагенты без имени** (чтобы не плодить тиммейтов) на диапазоне новых коммитов:

- **`qa-engineer`** (режим ревью) — всегда. Корректность + явная безопасность + конвенции +
  адекватность тестов. Промпт начинать с «Review mode.».
- **`devsecops-reviewer`** — если фича тронула хоть один путь:
  - security-проход: `apps/api/src/auth/`, `apps/api/src/common/guards|decorators/`,
    `apps/api/src/main.ts`, `apps/api/src/redirect/`, `apps/web/src/features/auth/`,
    `apps/web/src/stores/auth.store.ts`, `apps/web/src/lib/api-client.ts`
  - devops-проход: `.github/workflows/`, `apps/*/Dockerfile`, `nginx.conf.template`,
    `docker-compose.yml`, `turbo.json`, `**/.dockerignore`, `pnpm-workspace.yaml`,
    `pnpm-lock.yaml`, любой `package.json`, `config/env.validation.ts`

  Это НЕ опционально — если Шаг 1.2 отметил security-постуру или инфра-правку, прогон
  обязателен. Ревьюер делает только тот из двух проходов, чью зону diff реально задел.

Оба возвращают `{ findings: [{ file, line, summary, severity }] }`. Собрать в один отчёт
пользователю с пометкой от какого ревьюера (и `[security]`/`[devops]` для второго).
`severity: high` от любого — не пушим, пока не разобрано (Шаг 5).

Для особо чувствительного диапазона (auth, JWT, OAuth-флоу, CORS, публичный redirect,
платёжка) — **настоятельно** предложить пользователю эскалацию `/code-review high` или
`/code-review ultra` (глубокое облачное ревью, платно, запускает пользователь). Этот skill
его не запускает сам, но при `[security] high` от `devsecops-reviewer` — рекомендовать прямо.

## Шаг 5: правки

Разобрать находки вместе с пользователем. Мелкие однозначные — можно поручить
соответствующему тиммейту (если ещё жив) или починить в основной сессии; инфра-находки —
ваши. Спорные — решает пользователь.

## Шаг 6: ship

`/push-gate` — детерминированные проверки + свой advisory-проход, doc-sync, push.

## Завершение команды

После push попросить тиммейтов завершиться («Ask the be/fe teammate to shut down», и `qa`,
если спавнился под E2E). Общие директории команды чистятся автоматически при выходе из
сессии.
