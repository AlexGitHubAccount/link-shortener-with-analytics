# stage-review

Прогоняет для этапа `docs/stage-N-*.md` два последовательных захода ревью с расширением скоупа. Не хардкодит поиск багов сам — вызывает встроенные skills `code-review` и `security-review` с правильным скоупом и уровнем строгости на каждом заходе.

## Аргумент

Номер этапа (например `2`). Если не передан — спросить пользователя явно, для какого этапа запускать ревью, не гадать.

## Шаг 0: контекст

1. Прочитать `docs/stage-N-*.md` для этого номера — что этап должен был дать по плану, критерии верификации из раздела «Верификация».
2. Проверить, что тег `stage-(N-1)-done` существует (`git tag -l`) — это база для Захода 1. Если предыдущего тега нет **и N > 1** — сообщить пользователю и остановиться: без базовой точки Заход 1 не имеет смысла. **Особый случай N=1**: предыдущего тега не существует по определению (первый этап, диффить не с чем) — Заход 1 в этом случае пропускается, сразу выполняется только Заход 2 (весь код), т.к. для первого этапа «только новый этап» и «весь накопленный код» — это одно и то же.
3. **Важно про `security-review`**: этот skill не принимает путь/скоуп как аргумент — он всегда молча строит `git diff origin/HEAD...HEAD` через захардкоженную команду в своём frontmatter. Так как в проекте официально нет `origin` (GitHub-remote появится только на Этапе 7), нужен **локальный** ref: `git update-ref refs/remotes/origin/HEAD <commit>` — не настоящий remote, ничего никуда не пушится, просто git-указатель на диске. Перед Заходом 1 указать его на `stage-(N-1)-done` (или на корневой коммит для N=1). Он должен быть **реальным предком HEAD** (иначе `no merge base`) — брать тег/коммит из истории, не выдумывать «пустой» коммит без связи с репозиторием.

## Заход 1 — только новый этап (узкий скоуп)

Скоуп: `git diff stage-(N-1)-done..HEAD`.

1. `git update-ref refs/remotes/origin/HEAD stage-(N-1)-done` (для N=1 — на корневой коммит, `git rev-list --max-parents=0 HEAD`).
2. Запустить skill `code-review` на этом диффе, уровень строгости `medium`.
3. Запустить skill `security-review` (без аргументов — скоуп он берёт сам из `origin/HEAD`, который мы только что выставили).
4. Если есть находки — кратко объяснить пользователю, что нашли и почему это проблема, исправить, затем повторить шаги 2–3 на обновлённом диффе.
5. Максимум 3 итерации. Если после 3-й итерации всё ещё есть находки — остановиться, показать оставшиеся находки пользователю, **не переходить к Заходу 2 самостоятельно**.
6. Как только чисто — явно сообщить: «Заход 1 (скоуп: только Этап N) — чисто» и перейти к Заходу 2.

## Заход 2 — интеграция нового кода со всем накопленным

**Смысл**: проверить, как код нового Этапа N интегрируется со ВСЕМ кодом проекта от Этапа 1 до текущего. Ловит конфликты типов между модулями, несогласованность API, нарушения архитектурных границ — проблемы, видные только когда смотреть весь проект целиком, а не только изменённые строки.

**Скоуп**: пути `apps/api/src apps/web/src packages/` целиком — **полное сканирование ВСЕХ файлов**, не диф. Это показывает, как весь код целиком (все этапы вместе) соответствует друг другу.

**Почему не диф?** Диф показывает только изменённые строки. Но конфликты интеграции часто скрыты в **неизменённых файлах**:
- Модуль A (Этап 1, не менялся): `export function foo(id: number)`
- Модуль B (Этап 2, новый): `foo("123")` ← ОШИБКА! Но диф её не видит, потому что A не менялся.

Полное сканирование видит и A, и B вместе → поймёт конфликт.

**Шаги**:

1. Запустить skill `code-review` на путях `apps/api/src apps/web/src packages/`, уровень строгости `medium`.
2. **`security-review` в Заходе 2 не запускается**. Причина: каждый этап получает свой `security-review` в Заходе 1 на свежем, маленьком диффе (дешевле по токенам); к Заходу 2 весь код уже был security-scan'нут поэтапно. Заход 2 сосредоточен только на корректности интеграции (через `code-review`).
3. **Находки в Заходе 2 — ОБЯЗАТЕЛЬНО чинить сразу.** Если `code-review` найдёт проблемы интеграции: объяснить пользователю, чинить, затем повторить только Заход 2 (от шага 1) на обновлённом коде. **Не переходить на Заход 1** — его диф больше не актуален.
4. Максимум 3 итерации. Если после 3-й всё ещё есть находки — остановиться, показать пользователю, не идти на Завершение.
5. Как только полное сканирование путей чисто — явно сообщить: «Заход 2 (весь проект интегрирован) — чисто».

## Завершение

1. `git tag stage-N-done` на текущем HEAD.
2. Обновить статус этапа на ✅ в `docs/stage-N-*.md` и в таблице «Роадмап по этапам» в `docs/plan.md`.
3. Дать пользователю связную сводку: что искали на каждом заходе, что нашли, что починили, финальный вердикт.

## Опциональная эскалация

Для особо чувствительных этапов (явный кандидат — Этап 4, авторизация) пользователь может сам явно запустить `/code-review ultra` — глубокое многоагентное облачное ревью с перекрёстной проверкой находок между независимыми агентами. Это платно и должно быть инициировано пользователем напрямую в чате — этот skill не запускает `ultra` самостоятельно.
